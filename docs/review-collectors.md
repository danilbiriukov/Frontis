## 2. Покоммитный анализ

### `e7f6d1c` [feat] Базовая информация о проекте (#20)
*Файлы: `src/collectors/project-info.ts`, `docs/project-info.md`, `test/project-info.test.js`*

#### Сильные стороны
- Строгий порядок приоритета менеджеров пакетов: сначала поле `packageManager` в `package.json`, затем поиск lock-файлов в строгом порядке `pnpm-lock.yaml → yarn.lock → package-lock.json → npm-shrinkwrap.json`.
- Корректная изоляция Git: безопасно обрабатываются репозиторий без коммитов (`commit: null`), отсоединённый HEAD (`branch: null`) и каталоги вне Git (`git: null`).
- Ограничение по тайм-ауту (`GIT_TIMEOUT_MS = 10_000`) и проброс `context.signal`.
- В тестах применён `GIT_CEILING_DIRECTORIES = tmpdir()`, блокирующий случайный поиск вверх по дереву каталогов.

#### Внесённые исправления
- **Разбор строк Git (P3)**: в `readGit` строка 70 заменена на `log.split(/\r?\n/)`, что предотвращает сохранение `\r` на Windows при любых настройках `core.autocrlf`.

#### Дополнительные замечания
- Регулярное выражение `/^(npm|pnpm|yarn)@([^+\s]+)/` строго ограничено типами `PackageManager = 'npm' | 'pnpm' | 'yarn'`. Если в `package.json` указан `bun`, сборщик корректно откатывается к lock-файлу.

### `4cd0d05` [feat] Сборщик неиспользуемого кода (knip) (#24)
*Файлы: `src/collectors/knip.ts`, `docs/knip.md`, `test/knip.test.js`, фикстуры*

#### Сильные стороны
- Отказ от вызова `npx` в рантайме. Поиск бинарника через `createRequire(...).resolve('knip')` с подъёмом по каталогам до `package.json` knip обходит ограничение `ERR_PACKAGE_PATH_NOT_EXPORTED`.
- Кроссплатформенный запуск через `process.execPath` (Node.js) с файлом CLI knip (на Windows `.js` файлы напрямую через `execFile` не запускаются).
- Поддержка двух форматов отчёта: knip 5 (`output.files: string[]`) и knip 6 (`output.issues: [{ file, ... }]`).
- Обработка составных находок (`duplicates` и `cycles` приходят массивами объектов).
- Корректная обработка кодов возврата: knip возвращает код 1 при наличии находок, что трактуется как успешный аудит (`status: 'ok'`). Код 2 и выше перехватываются как `knip-failed`.
- Требование абсолютного `projectDir` строго закреплено в контракте, поэтому внутренний резолв `projectDir` не требуется.

### `0cc05f8` [feat] Сборщик форматирования (Prettier) (#40)
*Файлы: `src/collectors/prettier.ts`, `docs/prettier.md`, `test/prettier.test.js`*

#### Сильные стороны
- Проверка форматирования через API `prettier.check()` без записи на диск.
- Учитываются `.gitignore`, `.prettierignore`, `.editorconfig` и файлы настроек проекта.

- Файлы с синтаксическими ошибками выделяются в `errors` со статусом `prettier-error` (`severity: 'error'`), не маскируясь под неотформатированные.

#### Внесённые исправления
- В `docs/prettier.md` явно зафиксировано, что символические ссылки не проверяются (`entry.isFile()` игнорирует симлинки по стандарту).

### `a792d5c` [feat] Разбор итогов Jest и Vitest (#41)
*Файлы: `src/collectors/test-results.ts`, `docs/test-results.md`, `test/test-results.test.js`, фикстуры*

#### Сильные стороны
- Чтение готового артефакта без запуска тяжеловесных тестовых раннеров внутри аудита.
- Автоматическое определение Jest vs Vitest по маркерам `numRuntimeErrorTestSuites` / `wasInterrupted`.
- Извлечение строки упавшего теста из `location.line`.
- Очистка ANSI-кодов и служебных маркеров Jest (`stripVTControlCharacters`, удаление маркеров `●`).
- Корректная обработка упавших сьютов (`failedSuites`) и прерванных прогонов (`complete: false`).

#### Внесённые исправления
- **Соответствие контракту (P1)**: повреждённый JSON отчёта или формат не Jest/Vitest теперь возвращает `status: 'error'` с кодом `invalid-test-report` вместо `no-data`. Поведение зафиксировано в `docs/test-results.md` и покрыто тестом `test/test-results.test.js`.
- **Резолв путей (P2)**: в `toPath` путь нормализуется как `relative(projectDir, resolve(projectDir, file))`. Относительные пути в отчёте теперь корректно считаются от `projectDir`, вне зависимости от текущей рабочей директории процесса (`process.cwd()`). Добавлен регрессионный тест.

### `c4a8844` [feat] Где используются отстающие пакеты (#42)
*Файлы: `src/collectors/import-map.ts`, `docs/import-map.md`, `test/import-map.test.js`*

#### Сильные стороны
- Использование `git ls-files --cached --others --exclude-standard -z` исключает сканирование мусорных директорий и учитывает `.gitignore`.
- Высокая производительность: 244 файла в Teamer отсканированы за 65 мс.
- Точное сопоставление имени пакета: проверка границы имени исключает ложные срабатывания (`lodash/fp` относится к `lodash`, а `lodash-es` — нет).

- Отсутствие находок (только `data`): сборщик носит чисто информационный характер и не искажает общий балл аудита.

#### Внесённые исправления
- **Регистронезависимость расширений (P3)**: в `SOURCE_EXTENSIONS` добавлен флаг `/i`. Добавлен тест с расширением `.JS` в верхнем регистре.

### `978d023` [feat] Сверка версии Node.js с последней LTS (#27)
*Файлы: `src/collectors/node-version.ts`, `docs/node-version.md`, `test/node-version.test.js`*

#### Сильные стороны
- Поддержка всех форматов версий: точные (`22.12.0`), диапазоны (`>=20`, `^22`, `22.x`), алиасы `nvm` (`lts/*`, `lts/iron`, `node`, `current`).
- Локальный кэш на 24 часа в `.frontis/cache/node-releases.json` и режим `stale-cache` при отсутствии сети/тайм-ауте.
- Валидация кэша: защита от повреждённых данных и проверка перевода системного времени назад (`now >= cached.fetchedAt`).
- Ограничение сетевого запроса через `AbortSignal.timeout(10_000)` и объединение с внешним `signal` через `AbortSignal.any`.
- Градация важности находок по величине отставания: `major` (`error`), `minor` (`warning`), `patch` (`info`).

#### Внесённые исправления
- **Изоляция записи кэша (P1)**: в `loadReleases` операции `mkdir` и `writeFile` обёрнуты в отдельный `.catch(() => undefined)`. При сбое записи на диск (read-only FS, отсутствие прав) свежие данные из сети не теряются, и сборщик успешно возвращает результат с `origin: 'network'`. Поведение покрыто тестом `test/node-version.test.js`.

### `cf26cde` [feat] Размер сборки (#28)
*Файлы: `src/collectors/build-size.ts`, `docs/build-size.md`, `test/build-size.test.js`, `src/core/rules.ts`*

#### Сильные стороны
- Честный подсчёт размера существующей сборки без запуска сборщиков проекта.
- Корректное граничное условие: равенство лимиту `totalBytes === maxBytes` не считается превышением (`exceeded = totalBytes > maxBytes`).
- Выделение 5 крупнейших файлов со стабильной сортировкой по размеру и пути.
- Корректные причины для `no-data`: папка не существует, путь является файлом, нет прав на чтение, папка пуста.

#### Внесённые исправления
- **Устранение зависимости collectors от core (P2)**: константа `BYTES_IN_MB` перенесена в `src/collectors/build-size.ts` и экспортирована оттуда. Модуль `src/core/rules.ts` импортирует её из сборщика. Слой `collectors` теперь полностью автономен и не зависит от `core`.

#### Обоснованный отказ от P3 (source.file: buildDir)
- Решение не указывать `source: { file: buildDir }` полностью обосновано: по контракту `source.file` ожидает путь к конкретному файлу для подсветки в коде или аннотациях Code PushUp / IDE. Указание каталога сборки привело бы к битым ссылкам на несуществующий файл в отчёте.
