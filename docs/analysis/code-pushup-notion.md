# Code PushUp: проверка на реальном проекте

17.10.2026 · Юрий Трондин

Дополнение к «Frontis: конкурентный анализ». Здесь только то, что выяснилось при установке Code PushUp на живой проект и при чтении его кода. Обзор продукта и стратегии смотрите в основном документе.

## Итог

- **На реальном проекте Code PushUp (CP) показал заметно лучшую картину, чем есть на самом деле.** ESLint проверил 0 файлов и выдал 100%, TypeScript дал 124 ложные ошибки, critical-уязвимости почти не снизили оценку.
- **Встроенная интеграция с Nx упала сразу,** а без ручной настройки не заработали ESLint и TypeScript.
- **Задачу B5 («один модуль упал — остальные работают») CP не умеет:** упавший плагин роняет весь запуск.
- **Плагинов knip и размера сборки в npm нет.** C4 и C8 остаются нашими.
- **Для стратегий:** П2 (зависеть от плагинов CP) рискованнее, чем в матрице. В П3 данные, собранные плагинами CP, нужно проверять.

## Как проверяли

- **Версия:** Code PushUp 0.126.4.
- **Проект:** Teamer, Nx-монорепозиторий из 6 проектов (React + NestJS), pnpm, Windows 11, Node 26.
- **Плагины:** eslint, coverage, js-packages (audit и outdated), typescript, jsdocs.
- **Время:** установка 34 с, сбор 73 с (основное время — прогон тестов для покрытия).
- **Перепроверка:** каждую цифру сверили с прямым запуском инструментов. Исходники смотрели по тегу v0.126.4.

## Что показал CP и что на самом деле

| Проверка | CP показал | На самом деле |
| --- | --- | --- |
| ESLint | 100, «ESLint did not find any problems» | Проверено 0 файлов. С шаблоном по файлам нашлось 4 проблемы в 239 файлах |
| TypeScript | 124 ошибки, оценка 0 | Ложные срабатывания: плагин не учитывает `references` в tsconfig. `tsc -b` проходит без ошибок |
| Уязвимости | Security 80 | В dev-зависимостях 2 critical и 16 high. Dev идёт с весом 15 против 80 у prod, поэтому почти не влияет на оценку |
| Покрытие | Ветки 86%, функции 90%, строки 93% | Похоже на правду |
| Отчёт | `report.md` 740 КБ, `report.json` 3 МБ | Читать неудобно, по разделу на каждое правило ESLint, даже без нарушений |

## Найденные баги и уязвимости

1. **Nx-интеграция падает при загрузке конфига** (`Audit slugs must be unique`). CP разбирает конфиг ESLint сам, а не спрашивает у ESLint итоговые правила. Стандартный пресет Nx задаёт одно правило дважды с одинаковым по смыслу значением. CP считает это двумя правилами, даёт им одно имя и падает на собственной проверке.
2. **На Windows ESLint молча проверяет 0 файлов.** Команда идёт через cmd, который не раскрывает шаблоны вида `apps/*/src`, а флаг `--no-error-on-unmatched-pattern` прячет ошибку. На Linux тот же конфиг сработает, так что результат зависит от ОС.
3. **Упавший плагин роняет весь запуск.** Плагины идут по очереди, ошибки не перехватываются, ограничения по времени нет.
4. **Может удалить папку пользователя.** После работы плагина CP удаляет папку, в которой лежит его выходной файл. Если указать `outputFile: 'src/out.json'`, удалится вся `src` (видно по коду, сценарий не запускали).
5. **Команды запускаются через shell без экранирования аргументов.** Пути с пробелами ломаются, через `&` или `$()` можно выполнить чужую команду. Node сам предупреждает об этом при каждом запуске (DEP0190).
6. **Ошибка тестов в плагине покрытия подменяется общей фразой,** и плагин может молча взять старый отчёт.
7. **Сообщения инструментов не экранируются в markdown.** Отчёт идёт в комментарий к PR, так что код из чужого PR может вставить туда ссылки и картинки.
8. **Весь вывод инструментов хранится в памяти.** На больших репозиториях падает с ошибкой строки больше 512 МБ (их issue #865).

## Уточнения к сверке бэклога

Строки, где проверка расходится с таблицей в основном документе:

| Задача | Было | Стало | Почему |
| --- | --- | --- | --- |
| B4. Статусы в консоли | Совпадает | Частично | Ход по плагинам есть, статусов «ожидает / запущен / готово / ошибка» и итога по модулям нет |
| B5. Устойчивость к сбоям | Проверить руками | Нет | Проверено по коду: упал один плагин — упал весь сбор, ограничения по времени нет |
| C4. knip | Совпадает | Нет | Плагин есть только в репозитории сообщества: версия 0.0.0, в npm не опубликован, последний коммит в декабре 2025 |
| C6. Покрытие и тесты | Частично | Частично | Только покрытие из LCOV. Упавших и пропущенных тестов нет, ошибку теста прячет |
| C8. Размер сборки | Совпадает | Нет | Плагин есть только в репозитории сообщества, в npm не опубликован, последний коммит в декабре 2025 |

Итого по 13 задачам ядра и модулей сбора:
- совпадают полностью 4: B3, B6, C2, C3;
- частично 5: B4, B7, C1, C5, C6;
- у CP нет 4: B5, C4, C7, C8.

## Что это значит для решения

- **Гипотеза «CP не работает в контуре партнёра без доработок»** на Teamer подтвердилась частично: без ручной настройки не прошли ESLint и TypeScript. Корпоративный реестр и VPN не проверяли, это остаётся на тестовый проект партнёра.
- **П2.** Ошибки в данных приходят из плагинов CP, а исправить их без форка нельзя: только PR авторам или обходы в нашем конфиге. Оценка «Независимость от чужого кода» для П2 скорее завышена.
- **П3.** Формат `report.json` описан типами, но пакет моделей тоже версии 0.x. Если данные собирают плагины CP, Frontis должен их проверять: «проверено 0 файлов» — ошибка, а не 100%. ESLint и TypeScript, возможно, надёжнее собирать своими модулями.
- **Конфиг остаётся обязательным,** без него ошибка (решение Данила). Отличие «запуск без настройки» из позиционирования снимаем или переводим в мастер создания конфига.
- **Не проверяли:** мастер `npm init @code-pushup/cli` и `ncu --doctor`.

Подробный разбор с путями к файлам и номерами строк лежит в репозитории: `docs/analysis/code-pushup.md`.
