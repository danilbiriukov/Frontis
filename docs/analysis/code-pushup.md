# Анализ конкурента: Code PushUp

Дата: 13.10.2026. Версия: `@code-pushup/cli` 0.126.4.
Исходники: [github.com/code-pushup/cli](https://github.com/code-pushup/cli), тег v0.126.4 (ab6edf5), лицензия MIT.

## Кратко

Code PushUp (CP) — CLI, который запускает готовые инструменты (ESLint, coverage, npm audit, TypeScript и др.), сводит их результаты к оценкам 0–100 и сохраняет отчёт в `report.json` и `report.md`. Визуализация и история запусков есть только в их платном портале.

Мы проверили его на нашем проекте Teamer (Nx-монорепозиторий: React + NestJS, pnpm, Windows). Главный вывод: на реальном проекте CP показал заметно лучшую картину, чем есть на самом деле. ESLint проверил 0 файлов и выдал 100%, TypeScript дал 124 ложные ошибки, а критические уязвимости почти не снизили оценку безопасности.

## 1. Как устроен

Монорепозиторий Nx из 14 пакетов (пути ниже от `packages/`):

| Пакет | Что делает |
|---|---|
| `models` | Zod-схемы: конфиг, плагин, аудит, группа, категория, отчёт, дифф |
| `utils` | Запуск процессов, файлы, git, логгер, md-отчёт, скоринг, импорт конфига |
| `core` | Сбор → оценка → сохранение, сравнение отчётов, история, загрузка в портал |
| `cli` | Команды: `collect`, `upload`, `compare`, `history`, `merge-diffs`, `print-config` |
| `ci` | Прогон на base и head, дифф, комментарий в PR, поддержка монорепозиториев |
| `nx-plugin` | Генераторы и executor для Nx |
| `create-cli` | Мастер `npm init @code-pushup/cli`: генерирует конфиг, `.gitignore`, CI |
| `plugin-*` | eslint, coverage, js-packages, typescript, jsdocs, lighthouse, axe |

**Модель данных:**
- Плагин (`models/src/lib/plugin-config.ts:69`): `{slug, title, audits[], groups?[], runner}`.
- Runner — функция, возвращающая результаты аудитов, или внешняя команда, которая пишет JSON в файл (`runner-config.ts:27`).
- Результат аудита (`audit-output.ts:39`): `{slug, score 0..1, value, displayValue?, details?: {issues[], table}}`.
- Группа объединяет аудиты одного плагина, категория — аудиты и группы из разных плагинов. Обе задают веса. Итог считается как взвешенное среднее (`utils/src/lib/reports/scoring.ts:79`).
- Результат раннера проверяется zod-схемой и сверяется со списком аудитов (`core/src/lib/implementation/runner.ts:89-110`).

**Остальное:**
- Конфиг: ищется `code-pushup.config.{ts,mjs,js}`, грузится через bundle-require + esbuild (`utils/src/lib/import-module.ts:14`).
- Форматы отчёта: только `json` и `md` (`models/src/lib/persist-config.ts:4`), HTML нет.
- Кэш: `.code-pushup/<plugin>/runner-output.json`.
- Сравнение: `core/src/lib/compare.ts:86`, дифф двух `report.json` по категориям, группам и аудитам.
- История: `core/src/lib/history.ts:27`, по очереди переключает коммиты и собирает отчёт на каждом.
- CI: `ci/src/lib/run.ts`, `comment.ts`. Пишет комментарий в PR, умеет оставлять только проблемы в изменённых файлах (`issues.ts:27`).

## 2. Плагины и как они считают оценку

| Плагин | Что делает | Формула оценки |
|---|---|---|
| eslint | `npx eslint --format=json` | Аудит = правило. Оценка 1, если нарушений нет, иначе 0. Группа = доля правил без нарушений. **1 и 500 нарушений дают одинаковую оценку** |
| coverage | Опционально запускает тесты, читает только LCOV | covered/total отдельно для функций, веток и строк |
| js-packages (audit) | `npm/pnpm/yarn audit --json` | `max(0, 1 − critical − 0.1·high − 0.05·moderate − 0.02·low − 0.01·info)`. Группа: prod с весом 80, dev с весом 15 |
| js-packages (outdated) | `outdated --json` | `(total − major) / total`, minor и patch не учитываются |
| typescript | Компиляция через TS API | Аудит = категория диагностик, оценка 0 или 1 |
| jsdocs | ts-morph | Доля задокументированных сущностей |
| lighthouse | Chrome + Lighthouse | Оценка Lighthouse, при `null` ставится 1 |
| axe | Playwright + axe-core | Нарушения → 0, остальное → 1 |

### Найденные на прогоне баги

1. **Готовая интеграция с Nx падает сразу.** `eslintConfigFromAllNxProjects()` роняет загрузку конфига:
   ```
   SchemaValidationError: Invalid CoreConfig
   ✖ Audit slugs must be unique, but received duplicates: "no-cond-assign-4da1eac06e945b1a"
   ```
   Причина. Чтобы составить список аудитов, CP не спрашивает у ESLint итоговый конфиг. Он импортирует `eslint.config.mjs` и просто собирает все `rules` из всех блоков массива, игнорируя `files` и порядок переопределения (`meta/versions/flat.js`, `findEnabledRulesWithOptions`). В конфиге любого проекта Teamer правило `no-cond-assign` задано дважды:
   - блок 0 (пресет `@nx/eslint-plugin`, все файлы): `["warn", "except-parens"]`;
   - блок 5 (`@eslint/js` recommended, `*.ts`): `"error"`, без опций.

   Для ESLint это одно и то же: `except-parens` — значение по умолчанию. CP различает правила по хешу «сырых» опций, `[]` против `["except-parens"]`, и получает два правила. А слаг аудита он строит по опциям, в которые уже подставлен `meta.defaultOptions` (`meta/hash.js`, `meta/parse.js` → `resolveRuleOptions`). Оба правила получают один слаг, и собственная zod-валидация CP отклоняет конфиг.

   Сама `eslintConfigFromAllNxProjects()` ни при чём, она только находит 6 проектов с их конфигами. Ломается общая логика чтения flat-конфига, а наш стандартный пресет Nx как раз её задевает. Упавший конфиг роняет весь запуск, а не только ESLint.

2. **ESLint молча проверяет 0 файлов и рапортует 100%.** CP запускает `npx eslint ... --no-error-on-unmatched-pattern apps/*/src libs/*/src` через `shell: true`. На Windows cmd не раскрывает глобы, ESLint получает шаблон `apps/*/src`, который не совпадает ни с одним файлом. Флаг `--no-error-on-unmatched-pattern` прячет ошибку. На Linux/macOS тот же конфиг сработает: шаблон раскроет sh. То есть результат зависит от ОС.

3. **В отчёт попадают не все найденные проблемы.** ESLint нашёл проблемы по 2 правилам: 3 предупреждения `no-unused-vars` и ошибку «Definition for rule 'react-hooks/exhaustive-deps' was not found». CP пишет «2 audits failed», но в отчёте показан только один провалившийся аудит.

4. **README расходится с CLI.** Документация советует `npx code-pushup print-config` для просмотра аудитов, а команда падает с `Missing required argument: output`.

5. **Отчёт неудобно читать.** `report.md` весит 740 КБ (6600 строк, по разделу на каждое из 91 правила, даже без нарушений). `report.json` весит 3 МБ.

6. Node при каждом запуске выдаёт `DEP0190: Passing args to a child process with shell option true can lead to security vulnerabilities`.

## 4. Баги и уязвимости в исходном коде

**CONFIRMED** — путь в коде прочитан, **PLAUSIBLE** — вероятно, но не проверено до конца.

1. **CONFIRMED, высокая. Удаление папки пользователя.** После работы раннера вызывается `rm -rf path.dirname(outputFile)` (`core/src/lib/implementation/runner.ts:46`). При `outputFile: 'reports/eslint.json'` сотрётся вся папка `reports`, при `'src/out.json'` — `src`. При `'out.json'` удаляется `.`: на Windows падает с EBUSY, на Linux/macOS, вероятно, успеет удалить содержимое текущей папки (PLAUSIBLE). Схема разрешает в `outputFile` любую непустую строку.

2. **CONFIRMED, средняя. `shell: true` и аргументы без экранирования** (`utils/src/lib/execute-process.ts:164-167`).
   - Шаблоны eslint на Windows передаются без кавычек (`plugin-eslint/src/lib/runner/lint.ts:36-39`). Путь с пробелом разваливается, `&` и `|` выполнит cmd.
   - `objectToCliArgs` (`utils/src/lib/transform.ts:93`) оборачивает значения в `"..."` без экранирования, так что sh раскрывает внутри `$()`.
   - Ввод в основном из конфига, который и так исполняемый код. Поэтому это скорее надёжность, чем RCE, кроме CI с недоверенными путями.

3. **CONFIRMED, средняя. Весь вывод процесса хранится в памяти** (`execute-process.ts:173-191`), причём дважды. На больших монорепозиториях падает с `Cannot create a string longer than 0x1fffffe8` (issue #865).

4. **CONFIRMED, средняя. `history` без try/finally** (`core/src/lib/history.ts:37-70`). Если сбор упал, репозиторий остаётся в detached HEAD. С `--forceCleanStatus` перед каждым переключением выполняются `git reset --hard` и `git clean -fd` (`utils/src/lib/git/git.ts:95-97`): незакоммиченные изменения пропадают.

5. **CONFIRMED, средняя. Кэш не инвалидируется и не проверяется** (`runner.ts:136-156`). У `runner-output.json` нет ключа по коммиту, конфигу или файлам и нет проверки схемой. После изменений в коде отдаются устаревшие результаты.

6. **CONFIRMED, средняя. Инъекция в markdown.** `wrapTags` (`utils/src/lib/reports/formatting.ts:224`) экранирует только открывающие теги. `</details>`, `![](url)` и `[x](url)` проходят как есть, а сообщения TS и ESLint цитируют код. PR из форка может вставить в комментарий бота картинку-трекер или ссылку и сломать вёрстку. Эксплуатация на GitHub — PLAUSIBLE.

7. **PLAUSIBLE, средняя. Комментарий бота ищется только по маркеру,** без проверки автора (`ci/src/lib/comment.ts:11-24`). Любой участник может оставить комментарий с маркером, и CI упадёт на 403 при попытке его обновить.

8. **CONFIRMED, низкая. coverage глотает ошибку команды** (`plugin-coverage/src/lib/runner/runner.ts:31-38`). Вместо «команда не найдена» пишет «Make sure all your tests are passing». Может молча взять старый lcov, дата файла не проверяется.

9. **CONFIRMED, низкая. Вывод npm audit/outdated парсится без проверки формы** (`npm/audit-result.ts:11`, `outdated-result.ts:6`). Без lock-файла или офлайн падает невнятным `Cannot convert undefined or null to object`.

10. **CONFIRMED, низкая. lighthouse засчитывает аудиты, упавшие с ошибкой, как пройденные** (`score ?? 1`).

11. **CONFIRMED, низкая. Ключи скоринга могут совпасть** (`scoring.ts:27,57`). Ключ строится как `${plugin}-${slug}`, а слаги содержат `-`: плагин `a-b` с аудитом `c` совпадёт с плагином `a` и аудитом `b-c`.

12. **CONFIRMED, низкая. Секреты.** apiKey передаётся аргументом `--upload.apiKey` и виден в списке процессов. Nx-executor пишет env и полную команду в лог (`nx-plugin/src/executors/cli/executor.ts:43-52`).

13. **CONFIRMED, низкая. `npx eslint` может скачать пакет из реестра,** если он не установлен локально: неожиданная версия, риск supply chain.

14. **CONFIRMED, низкая. Из нескольких конфигов берётся первый,** остальные молча игнорируются (`read-rc-file.ts:51`). У Frontis в этом случае ошибка, так правильнее.

15. **Производительность.** `calculateConfigForFile` вызывается по очереди на каждый файл (`lint.ts:54-82`). В `reduce` везде spread, что даёт O(n²).

Открытые баги на GitHub (метка bug): #865 (строка > 512 МБ), #879 (не парсится `yarn npm audit` v2), #1286 (мастер ставит порт 4200 вместо 5173 у Vite), #538 (Lighthouse нестабильно подключается к Chrome), #1084 (флаки-тесты executeProcess), #1094 (ошибка в github-action).

## 5. Что взять во Frontis

Брать идеи и формулы, код писать свой.

- **Иерархия «аудит → группа → категория»** с весами и оценкой 0..1 (0–100 в отчёте).
- **Проверка схемой того, что вернул каждый сборщик данных.** Не доверять JSON инструмента.
- **Единый формат проблемы** `{severity, message, file, line}`. На нём строится и HTML-отчёт, и фильтр «только изменённые файлы».
- **`report.json` рядом с HTML.** Это даст сравнение двух запусков («стало лучше/хуже») и комментарий в PR.
- **Пороги оценки и код выхода** для CI: упасть, если категория ниже N.
- **Определение пакетного менеджера по lock-файлу и монорепозитория** (pnpm/yarn/npm workspaces, Nx).
- **Мастер `init`:** находит eslint-конфиг, tsconfig, тест-раннер и пакетный менеджер, генерирует `frontis.config.ts`.

## 6. Что сделать лучше

- **HTML-отчёт как главный результат,** один файл, офлайн, без портала. Это наше основное отличие.
- **Если инструмент проверил 0 файлов, это ошибка, а не 100%.** Показывать, сколько файлов проверено.
- **ESLint оценивать с учётом количества нарушений** (на файл или на тысячу строк), а не 0/1.
- **Critical-уязвимости не размазывать весами.** Даже в dev-зависимостях они должны заметно бить по оценке. Учитывать, прямая зависимость или транзитивная и есть ли фикс. В outdated учитывать minor с меньшим весом.
- **TypeScript проверять с учётом project references** (`tsc -b`) или брать результат проектного typecheck.
- **Запуск процессов без shell:** cross-spawn или `node <bin.js>` пакета. Вывод инструмента писать в файл (`eslint -o`), а не держать в памяти.
- **Никогда не удалять папки пользователя.** Временные файлы только в своей tmp-папке.
- **Ошибки инструментов показывать как есть** (stderr, код выхода), по-русски и с подсказкой. Если упал один сборщик, это блок в отчёте, а весь запуск продолжается.
- **Экранировать в HTML всё, что пришло от инструментов:** в сообщениях есть код.
- **Кэш только с ключом** (lock-файл + конфиг + HEAD) или не делать вообще.
- **Брать инструменты из `node_modules` проекта, а не через `npx`.** Если инструмента нет, понятная ошибка «установите knip».

Чего у CP нет, а у нас будет: **knip** (мёртвый код и неиспользуемые зависимости) и **результаты прогона тестов** jest/vitest. CP берёт только coverage из lcov.

## 7. Чего не брать

- Портал, загрузку отчётов, GraphQL.
- `history` с переключением коммитов: опасно и долго.
- lighthouse и axe на первом этапе: нужен Chrome или Playwright, работают нестабильно (#538).
- Nx-плагин и jsdocs-плагин.
- Монорепозиторий из 14 пакетов: Frontis хватит одного пакета с папками `core`, `collectors`, `report`.

## 8. Если подключать CP как зависимость

Это вариант, который предложил Данил: не форкать CP и не писать с нуля, а поставить его зависимостью и делать свои модули поверх.

**Куда CP можно расширять:**
- **Свои плагины.** Это официальный путь: плагин — объект `{slug, audits, groups, runner}`, его подключают в `code-pushup.config.ts`. Так можно сделать модули knip и «результаты тестов» (у CP их нет).
- **Свой отчёт.** CP сохраняет `report.json` с понятной схемой (`@code-pushup/models`). Его можно прочитать и нарисовать свой отчёт: HTML, по-русски, с кнопкой перезапуска.
- **Своя обвязка.** Свой CLI, который запускает `collect`, а потом делает своё: отчёт, интеграции с трекером.

**Модули из списка Данила:**
- **Локализация.** Встроенной i18n в CP нет. Тексты отчёта и консоли зашиты по-английски (`utils/src/lib/reports/generate-md-report.js`, `log-stdout-summary.js`). Перевести их можно, только переписав рендер отчёта. Реально это означает свой отчёт из `report.json`, а названия аудитов приходят из ESLint и прочих инструментов по-английски.
- **Интеграция с таск-трекером.** Читаем `report.json` и создаём задачи по провалившимся аудитам. От CP нужен только JSON, это хорошо ложится на вариант «зависимость».
- **Кнопка перезапуска.** В md-отчёте её не сделать, нужен свой HTML-отчёт и локальный сервер или команда.

**Риски варианта «зависимость»:**
- Баги CP мы получаем вместе с ним. Всё из раздела 3 мы уже поймали на Teamer: Nx-интеграция падает, на Windows ESLint проверяет 0 файлов, TypeScript даёт ложные ошибки. Исправить их у себя без форка нельзя: только PR в их репозиторий или обходы в нашем конфиге.
- Модели и оценки остаются их: бинарный ESLint и веса уязвимостей мы не поменяем, разве что заменим их плагины своими.
- Релизы частые (0.x, ломающие изменения возможны). Версию нужно жёстко фиксировать.
- В `develop` уже есть своя схема конфига, статусы, важность и оценка проекта (коммиты `b23bf22`, `11e9b8a`). При переходе на CP это частично дублирует `@code-pushup/models`, нужно решить, что оставляем.
