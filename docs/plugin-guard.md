# Запуск плагинов с обработкой сбоев

`runGuardedPlugins(projectDir, plugins)` принимает список плагинов и настройки `enabled` и `timeoutMs` для каждого из них. `slug` задаёт идентификатор плагина в диагностике. У отключённого плагина фабрика не вызывается.

Для включённого плагина `module` задаёт имя пакета, доступного из установки Frontis, или абсолютный `file:` URL. Модуль экспортирует `prepare(options, outputDir)`, которая возвращает стандартный `PluginConfig` или причину пропуска с полями `code`, `reason` и `action`. Передаваемые `options` должны сериализоваться для передачи дочернему процессу. Рабочий каталог процесса совпадает с корнем проекта. Конфигурация Code PushUp создаётся в памяти. Временные файлы плагина можно хранить в выделенном `outputDir`, который очищается после запуска.

После запуска движок проверяет формат отчёта. Необязательная функция `validate(report, options, outputDir)` проверяет данные конкретного плагина и возвращает причину пропуска или `undefined`. Например, обёртка ESLint может передать в проверку число файлов из исходного результата ESLint. Ноль файлов даёт причину `no-files`, а проверенный файл без нарушений остаётся успешным результатом. В аудитах ESLint 0.126.4 счётчика файлов нет. [Проверка совместимости](code-pushup-compatibility/README.md)

Тайм-аут включает загрузку фабрики, выполнение плагина и проверку результата. По истечении срока Frontis останавливает дерево процессов плагина и запускает следующий. В `reports` попадают только проверенные отчёты. Если сборщик передал `CollectorRunError`, его причина и подсказка сохраняются.

`.frontis/no-data.json` содержит массив причин последнего завершённого запуска. У записи есть `plugin`, `code`, `reason` и `action`. Записи о сбоях и недоступных данных также содержат `logFile` с путём от `.frontis`. При успешном запуске всех плагинов записывается пустой массив. Технический журнал в `.frontis/logs/` хранит сведения о сбоях и до 65 536 последних символов вывода каждого плагина.
